2研究问题与实验设计

本阶段实验围绕以下四个核心研究问题展开，每个问题对应一组或多组对照实验：

RQ1
不同提示词策略（Zero-shot / Few-shot / CoT）对恶意代码识别效果的影响如何？哪种策略综合表现最优？
RQ2
两阶段检测方案在不同 LLM 模型（DeepSeek vs 通义千问）上的一致性如何？方案是否具备跨模型泛化能力？
RQ3
LLM 方案对混淆恶意代码的识别能力如何？与传统工具相比，在各类混淆技术上是否存在显著差异？
RQ4
LLM 方案与基于规则引擎的传统 WebShell 扫描工具相比，在准确率、误报率、漏报率等核心指标上的优势幅度如何？

3.2 分析与发现

3.2.1 Few-shot 策略表现最优

Few-shot 策略在准确率（98.45%）、召回率（96.76%）、F1（98.35%）三个核心指标上均领先，且 零未分类样本。其优势主要源于：

  • 示例引导：3 条精选示例（含 1 条 WebShell、1 条 SQLi、1 条良性代码）使模型快速建立对任务格式的认知，输出 JSON 结构更加规范；
  • 格式稳定性：启用 JSON 模式后，Few-shot 的输出格式一致性显著优于 CoT 的自由文本输出；
  • 混淆识别提升：相比 Zero-shot，Few-shot 的混淆识别率从 95.0% 提升至 99.0%，提升 4 个百分点。

3.2.2 Zero-shot 策略基础表现良好

Zero-shot 策略在不提供任何示例的情况下，仍达到 97.28% 的准确率，表明 DeepSeek 模型本身具备较强的恶意代码识别先验知识。其 14 条漏报中有 5 条为未分类（输出解析失败），主要出现在长文本或罕见语言（ASP/JSP）样本上。

3.2.3 CoT 策略输出格式不稳定

CoT（思维链）策略在理论上通过分步推理可提升复杂样本的识别精度，但实际表现最差，准确率仅 86.21%。核心问题在于：

CoT 的致命弱点：输出格式不稳定 CoT 策略要求模型输出自由文本推理过程，但模型经常在推理后忘记输出 JSON 格式的最终判定，导致 63 条样本（12.2%）无法解析。在 100 条混淆样本中，仅 49 条被正确识别（49.0%），51 条因格式问题被标记为错误。

尽管 CoT 策略的精确率为 100%（即所有被成功解析的结果均正确），但 71 条漏报中有 63 条（88.7%）是因格式问题而非识别错误造成。这表明 CoT 的识别能力本身不弱，但输出工程的缺陷严重制约了其可用性。

5.4 关键发现

5.4.1 LLM 方案在所有混淆技术上表现均衡

两阶段方案和 Few-shot 方案在 string_split、xor、comment_bypass 三种混淆技术上均达到 100% 识别率，仅在 base64 上有 1 条误判（96.6%）。这表明 LLM 能够理解混淆后的代码语义，而非仅依赖模式匹配。

5.4.2 传统工具在 string_split 上存在明显短板

传统规则引擎在 string_split（字符串拆分重组）混淆上仅识别 61.9%（21 条中仅 13 条正确），这是其最大的弱点。string_split 通过将关键词拆分为多个字符串片段后动态拼接，有效规避了基于字符串匹配的规则检测。相比之下，LLM 方案达到 100%，提升 38.1 个百分点。

5.4.3 传统工具在 base64 上反而表现最佳

传统工具在 base64 混淆上达到 100% 识别率，优于 LLM 的 96.6%。这是因为 base64 编码后的字符串具有明显的特征模式（如 eval(base64_decode(...))），规则引擎可以精确匹配此类已知模式。LLM 的 1 条误判出现在一个编码后内容极短的样本上，模型倾向于将其判定为良性。

5.4.4 CoT 策略在混淆样本上表现最差

CoT 策略在混淆样本上仅识别 49%（100 条中 49 条正确），51 条因输出格式问题被标记为错误。这与全量实验中的表现一致，进一步验证了 CoT 的格式不稳定问题是系统性的，而非样本相关的。

RQ3 结论 LLM 两阶段方案在混淆对抗上全面优于传统工具，总体识别率 99.0% vs 92.0%。最大优势体现在 string_split 混淆上（100% vs 61.9%），这是传统工具最大的盲区。LLM 的语义理解能力使其能够识破字符串拆分等语义级混淆，而规则引擎仅依赖模式匹配，无法应对未知的混淆变体。

6.2 优势分析

6.2.1 零误报：LLM 方案的核心优势

传统工具产生 50 条误报（FP），即 50 条良性样本被误判为恶意，误报率达 18.7%（50/268）。LLM 方案实现 零误报，精确率达 100%。这对于实际部署至关重要——高误报率会导致安全团队疲于审查告警，降低工具的可信度。

传统工具漏报 39 条恶意样本（漏报率 15.8%），LLM 方案仅漏报 8 条（漏报率 3.2%）。LLM 的语义理解能力使其能识别规则未覆盖的新型恶意代码模式。

在恶意代码类型（WebShell/SQLi/后门）和混淆技术的分类一致性上，LLM 方案达 90.69%，传统工具仅 78.14%。LLM 不仅能判断是否恶意，还能准确分类恶意类型，为后续处置提供更丰富的信息。

7两阶段管道效率分析

7.1 管道架构

两阶段检测管道是本课题的创新点，其设计理念为：用成本较低的 Few-shot 快速初筛全部样本，仅对置信度低于阈值的可疑样本触发 CoT 深度复审。这一设计在保持高精度的同时大幅降低了 CoT 策略的调用频率和总体延迟。

7.3 效率分析

两阶段管道的核心效率优势在于：仅 0.58%（DeepSeek）和 0.39%（通义千问）的样本触发了 CoT 复审，而独立 CoT 方案需对 100% 的样本进行思维链推理。这意味着：

  • 相比独立 CoT 方案，两阶段管道将 CoT 调用次数减少了 99.4%；
  • Stage2 仅增加 58.7s（DeepSeek）/ 14.5s（Qwen）的额外耗时，占总耗时的 10.7% / 5.5%；
  • CoT 复审成功纠正了 2/3（DeepSeek）和 1/2（Qwen）的低置信度样本判定，有效提升了边界样本的准确性；
  • 通义千问得益于 98.84% 的缓存命中率（515 条中 511 条命中缓存），总耗时仅 263.9s。

7.4 Stage2 纠正效果

DeepSeek 的 3 条 Stage2 复审样本中，2 条被 CoT 成功纠正（从错误判定改为正确判定），纠正率达 66.7%。这验证了两阶段管道的设计价值：Few-shot 对高置信度样本足够可靠，CoT 复审能有效处理少数边界样本。

8一致性与稳定性分析

8.1 同策略同模型多次运行一致性

2 条不一致样本均为 WebShell 类别（vbencode-bypass.asp 和 spexec.aspx），属于 ASP/ASPX 语言的边界样本。这些样本在训练数据中相对罕见，模型对其判定存在轻微波动。

8.2 跨策略一致性

Few-shot 与 CoT 策略的跨策略一致率为 87.57%（451/515），低于同策略一致性。这是预期结果——CoT 的 63 条未分类样本无法与 Few-shot 的判定对比，导致一致率下降。若排除 CoT 的未分类样本，有效对比的一致率将显著提升。

8.3 跨模型一致性

如第 4 节所述，DeepSeek 与通义千问的跨模型一致率为 99.22%（507/511），仅 4 条样本存在分歧。两个模型在 FP 和 FN 上完全一致（FP=0, FN=8），表明两阶段方案对模型选择不敏感。

10局限性讨论

10.1 CoT 策略的输出工程问题

CoT 策略虽然理论上可通过分步推理提升复杂样本的识别精度，但实际应用中 12.2% 的样本因输出格式不稳定而无法解析。这一问题的根源在于：自由文本推理模式缺乏结构约束，模型在推理过程中容易"忘记"输出最终的 JSON 判定。未来可通过以下方式改进：

  • 使用结构化输出约束（如 XML 标签包裹推理过程和最终判定）；
  • 采用 ReAct 框架将推理与行动分离；
  • 使用 function calling 强制 JSON 输出格式。

10.2 ASP/ASPX 语言覆盖不足

两个 LLM 模型在 ASP/ASPX 样本上的表现均弱于 PHP/Python，漏报中有 50% 来自 ASP/ASPX。这反映了训练数据分布的不均衡性。可通过在 Few-shot 示例中增加 ASP/ASPX 样本或使用专门的 ASP/ASPX 提示词模板来改善。

10.3 API 成本与延迟

LLM 方案的平均延迟为 4.3 秒/条（DeepSeek），远高于传统工具的近零延迟。全量 515 条实验消耗约 2.83M Tokens，成本约 50-60 元人民币。对于大规模文件扫描场景，成本和延迟可能成为瓶颈。两阶段管道通过仅在 0.58% 的样本上触发 CoT，有效控制了成本，但仍需依赖网络连接。

10.4 数据集规模与多样性

数据集 515 条样本虽然覆盖了四种混淆技术和三种语言，但样本量相对有限。此外，混淆变种均为已知混淆技术的自动化生成，未涵盖真实攻击者使用的新型混淆手法。未来需扩大数据集规模并引入真实攻击样本。

10.5 静态分析局限性

本研究仅进行静态文本分析，未执行恶意代码。某些动态行为（如运行时反射、动态加载）可能无法通过静态分析捕获。但考虑到安全要求，静态分析是合理的选择。

10.6 单次实验与统计显著性

虽然一致性分析表明 LLM 输出高度稳定（99.61%），但主实验为单次运行结果。理想情况下应进行多次重复实验并报告置信区间。不过，temperature=0.1 的设置和一致性验证在一定程度上弥补了这一局限。

11结论与后续展望

11.1 核心结论

本阶段实验围绕四个研究问题，在全量 515 条样本上进行了系统评估，得出以下核心结论：

研究问题核心结论关键数据
RQ1 策略对比Few-shot 综合最优，CoT 因格式问题不适合独立使用F1: 98.35% vs 83.22%
RQ2 跨模型一致性两阶段方案在两个模型上表现高度一致一致率 99.22%
RQ3 混淆对抗LLM 全面优于传统工具，string_split 优势最大99.0% vs 92.0%
RQ4 vs 传统工具LLM 在所有核心指标上全面领先F1 +16.0%, FP 0 vs 50

11.2 创新点验证

两阶段管道（Few-shot 快筛 + CoT 复审）作为本课题创新点，经实验验证具备以下优势：

  • 精度保障：F1 与 Few-shot 持平（98.35%），类型一致率优于 Few-shot（90.69% vs 88.26%）；
  • 效率优化：仅 0.58% 样本触发 CoT，比独立 CoT 减少 99.4% 的调用次数；
  • 跨模型泛化：在两个不同 LLM 上表现一致，不依赖特定模型；
  • 纠正效果：Stage2 成功纠正 66.7% 的低置信度样本。

11.3 后续展望

  1. Flask Web 可视化界面：实现交互式检测平台，支持文件上传、实时检测和结果可视化，作为答辩加分项；
  2. CoT 输出优化：尝试结构化输出约束（ReAct 框架或 function calling），解决 CoT 格式不稳定问题；
  3. 数据集扩展：引入更多 ASP/ASPX/JSP 样本和真实攻击样本，提升语言覆盖度；
  4. 分层架构探索：构建"传统工具初筛 + LLM 深度复核"的混合检测管道，兼顾效率与精度；
  5. 对抗样本研究：探索针对 LLM 的对抗性代码（如通过注释注入误导模型判定），评估方案的鲁棒性。
